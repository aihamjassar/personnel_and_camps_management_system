# حزمة النشر التجريبي

تُجهّز هذه الحزمة بيئة Docker Compose لتطبيق أكاديمي ببيانات اصطناعية فقط: PostgreSQL 16، API، واجهة React خلف Caddy، ونسخ احتياطي مشفّر يومي. **لم تُنشر الحزمة على مضيف عام**؛ يلزم اسم نطاق ومضيف Docker متاح قبل اعتمادها كبيئة staging فعلية.

## المتطلبات قبل النشر

- مضيف Linux مُدار من الفريق مع Docker Compose v2، جدار ناري يسمح بالوصول الوارد إلى TCP 80/443 وUDP 443، ونسخ احتياطي لمجلدات Docker volumes خارج المضيف.
- اسم نطاق فرعي تملكه الجهة، مع سجلات DNS تشير إلى المضيف. يطلب Caddy شهادة TLS تلقائيًا؛ يلزم أن يكون النطاق قابلًا للوصول من الإنترنت.
- بيانات قاعدة وأسرار فريدة للبيئة، ومفتاح `age` عام للنسخ الاحتياطية. لا تضع بيانات تشغيلية حقيقية في هذه البيئة الأكاديمية.

## الإعداد

1. من جذر المشروع:

   ```bash
   cp deploy/staging/.env.example deploy/staging/.env
   chmod 600 deploy/staging/.env
   ```

2. ولّد قيمًا قوية لكل من `POSTGRES_PASSWORD` و`JWT_SECRET`، مثل `openssl rand -hex 32`. ولّد مفتاح النسخ الاحتياطي على جهاز آمن:

   ```bash
   age-keygen -o /secure/path/staging-backup.agekey
   chmod 600 /secure/path/staging-backup.agekey
   ```

   انسخ **السطر العام فقط** (`age1…`) إلى `BACKUP_AGE_RECIPIENT`، واحتفظ بالملف الخاص خارج مستودع Git والمضيف المنشور. خزّن `BOOTSTRAP_ADMIN_PASSWORD` مؤقتًا في ملف `.env` المحلي المحمي.

3. عيّن `STAGING_DOMAIN` إلى نطاق DNS الحقيقي. تجنّب الأحرف المحجوزة في `POSTGRES_PASSWORD` أو استخدم قيمة سداسية عشرية مولّدة، لأن اتصال قاعدة البيانات يستخدم URL.

4. تحقق من ملف Compose ثم شغّل البيئة:

   ```bash
   docker compose --env-file deploy/staging/.env -f deploy/staging/compose.yaml config
   docker compose --env-file deploy/staging/.env -f deploy/staging/compose.yaml up -d --build
   docker compose --env-file deploy/staging/.env -f deploy/staging/compose.yaml --profile bootstrap run --rm bootstrap
   ```

   خدمة `bootstrap` تنشئ حساب المدير بكلمة مرور `BOOTSTRAP_ADMIN_PASSWORD` دون تمريرها إلى API أو تسجيلها. بعد التهيئة احذف هذا المتغير من ملف `.env` أو امسح قيمته، ثم غيّر كلمة المرور من إدارة المستخدمين. بذرة التطوير المحلية وحدها تحتفظ بالاعتماد الأكاديمي الافتراضي `admin / Admin@1234`؛ يرفض مسار الإنتاج إنشاء مدير بلا سرّ bootstrap.

5. تحقق من `https://$STAGING_DOMAIN/` ومن `/api/v1/health`، وراجع سجلات `web` و`api`. لا تعتبر إنشاء الحاويات دليلًا على صدور شهادة TLS أو نجاح الوصول العام؛ اختبر النطاق من شبكة خارجية.

## النسخ الاحتياطي والاستعادة

- تعمل خدمة `backup` كل يوم عند 02:00 UTC، وتكتب تفريغًا مخصصًا مشفّرًا إلى `backup_data` مع صلاحيات ملفات مقيدة وتحذف نسخًا أقدم من `BACKUP_RETENTION_DAYS` (14 يومًا افتراضيًا).
- هذا المجلد volume محلي على المضيف؛ **ليس نسخة خارج الموقع**. انسخ النسخ المشفّرة دوريًا إلى تخزين خارجي محمي، وراقب سجل الخدمة.
- للاستعادة: انسخ ملف `.dump.age` وملف المفتاح الخاص إلى جهاز آمن، ثم فكّه باستخدام `age -d -i staging-backup.agekey -o database.dump file.dump.age`، وتحقق من أرشيفه بـ `pg_restore --list database.dump`. نفّذ الاستعادة على قاعدة منفصلة بعد موافقة مالك البيئة، ثم راجع البيانات والتدقيق قبل تحويل المرور.

## حدود النشر

- النشر الحالي غير مُنفّذ لأن المستودع لا يحدد مضيفًا أو نطاقًا مخولًا، وبيئة Sandbox مؤقتة وغير مناسبة لاستضافة قاعدة دائمة.
- الخدمة التجريبية لا تُعدّ إنتاجًا، وCaddy لا يستطيع إصدار شهادة موثوقة قبل ربط DNS وفتح المنافذ.
- النسخ المشفّرة على المضيف لا تحقق وحدها متطلب النسخ خارج الموقع؛ يلزم تحديد مزوّد تخزين ومالك مسؤول عن اختبارات الاستعادة.
- قبل تعريض الخدمة للإنترنت، عالج نتائج `npm audit --omit=dev` الحالية (7 تحذيرات إنتاجية: 3 عالية و4 متوسطة) واختبر الترقيات؛ لم تُطبّق ترقيات رئيسية تلقائيًا.
