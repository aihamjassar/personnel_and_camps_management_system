# مواصفات واجهة وتجربة المستخدم (UI/UX Specification)

---

## 1. المبادئ التصميمية العامة

مستمدة من المتطلبات غير الوظيفية (القسم 11 من دراسة الجدوى):

| المبدأ | المتطلب المرتبط | التطبيق التصميمي |
|---|---|---|
| البساطة والوضوح | Usability | إنجاز المهام الأساسية دون تدريب مطوّل |
| إمكانية الوصول | Accessibility (WCAG) | تباين ألوان كافٍ، دعم لوحة المفاتيح، نصوص بديلة |
| الاستجابة السريعة | Performance | مؤشرات تحميل (Loading States) لأي طلب > 300ms |
| التصميم المتجاوب | — | يعمل على الحاسوب المكتبي والأجهزة اللوحية على الأقل |
| اتساق العرض | Maintainability | مكوّنات UI موحّدة يُعاد استخدامها عبر كل الوحدات |
| دعم اللغة العربية | — | تخطيط RTL كامل مع دعم أرقام/تواريخ محلية |

## 2. نظام الألوان والحالة (Design Tokens المقترحة)

| الحالة | اللون الدلالي | الاستخدام |
|---|---|---|
| نجاح (Success) | أخضر | تأكيد حفظ، حالة "نشط" |
| تحذير (Warning) | أصفر/برتقالي | حالة "إجازة"، "منتدب" |
| خطر (Danger) | أحمر | حذف، حالة "منتهي الخدمة"، رفض طلب نقل |
| معلومة (Info) | أزرق | إشعارات عامة، حالة "قيد المراجعة" |
| محايد | رمادي | نصوص ثانوية، حقول معطّلة |

## 3. مكوّنات الواجهة القياسية (Reusable Components)

1. **Sidebar تنقّل ديناميكي** — يُبنى في وقت التشغيل حسب صلاحيات الدور (RBAC)، وليس Hardcoded.
2. **جدول بيانات موحّد (DataTable)** — يدعم: الفرز، الفلترة، البحث، Pagination — يُستخدم في الأفراد، المعسكرات، المستخدمين، سجلات التدقيق.
3. **نموذج ديناميكي (Form Builder)** — لتوليد نماذج الإضافة/التعديل بحقول متشابهة البنية عبر الوحدات.
4. **بطاقة إحصائية (Stat Card)** — تُستخدم في لوحة التحكم الرئيسية لعرض المؤشرات المجمّعة.
5. **مكوّن حالة (Status Badge)** — لعرض حالة الفرد أو حالة طلب النقل بلون دلالي.
6. **مكوّن تأكيد إجراء (Confirmation Modal)** — إلزامي قبل أي عملية حذف أو تغيير حسّاس (مثل تفعيل نقل).
7. **مركز الإشعارات (Notification Center)** — قائمة منسدلة من الـ Topbar.

## 4. تدفقات تجربة المستخدم الحرجة (Critical UX Flows)

### أ) تدفق إضافة فرد جديد
`زر "+ إضافة" → نموذج منبثق → تحقق لحظي من الحقول (Client-side) → إرسال → مؤشر تحميل → رسالة نجاح Toast → تحديث الجدول تلقائيًا دون إعادة تحميل الصفحة`

### ب) تدفق طلب انتقال (الأكثر حساسية من ناحية UX)
`اختيار الفرد → اختيار المعسكر الهدف → عرض السعة المتبقية فورًا (Live Feedback) → تأكيد (Modal) → إرسال → عرض حالة الطلب (قيد المعالجة/مقبول/مرفوض) بوضوح`

### ج) تدفق التقارير
`اختيار نوع التقرير والفلاتر → معاينة سريعة (Preview) قبل التصدير → اختيار الصيغة (PDF/Excel) → تنزيل`

## 5. إمكانية الوصول (Accessibility) — متطلبات ملموسة

- تباين ألوان يحقق الحد الأدنى AA وفق WCAG للعناصر الرئيسية.
- كل حقل إدخال له `label` مرتبط برمجيًا (ليس Placeholder فقط).
- إمكانية التنقل الكامل عبر لوحة المفاتيح (Tab / Enter / Esc لإغلاق النوافذ المنبثقة).
- رسائل الخطأ نصية واضحة (ليست معتمدة على اللون وحده).

---

## 6. حالات الواجهة الإلزامية لكل شاشة بيانات

كل شاشة تعرض بيانات (جدول/قائمة) يجب أن تصمَّم لأربع حالات:

1. **Loading** — أثناء انتظار الاستجابة.
2. **Empty** — لا توجد بيانات (مع رسالة توجيهية، مثل "لا يوجد أفراد مسجّلون بعد").
3. **Error** — فشل الطلب (مع خيار "إعادة المحاولة").
4. **Success/Populated** — البيانات معروضة بشكل طبيعي.

---

## 7. النماذج الأولية (Wireframes) — حسب الجدول الزمني

وفق الجدول الزمني (الأسبوع 6)، يُطلب إنتاج نماذج تصميم أولية (Wireframes منخفضة الدقة) لكل الشاشات المذكورة في `Website-Structure-Page.md` قبل بدء التطوير الفعلي في الأسبوع 7 — لضمان اتفاق الفريق على البنية قبل كتابة الكود.

**قائمة الشاشات ذات الأولوية للـ Wireframes (Must-Have أولًا):**
1. تسجيل الدخول
2. لوحة التحكم الرئيسية
3. قائمة الأفراد + نموذج إضافة/تعديل
4. قائمة المعسكرات
5. إدارة المستخدمين والأدوار
6. نموذج طلب الانتقال
7. شاشة التقارير الأساسية
