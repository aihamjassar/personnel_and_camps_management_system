# تسلسل الإجراءات (Flow of Action)

> يوضح هذا الملف تسلسل تنفيذ الإجراء عبر الطبقات المعمارية الست للنظام (Client → Presentation → API → Business Logic → Integration → Database)، لكل عملية رئيسية.

---

## 1. التدفق العام الموحّد (ينطبق على أي إجراء كتابة/قراءة)

```
[1] Client (React.js SPA)
      │  يرسل الطلب مع رمز JWT في الـ Header
      ▼
[2] Presentation / Frontend Layer
      │  لوحات التحكم، النماذج، عرض النتائج
      ▼
[3] API Layer (REST / JSON)
      │  التحقق من التنسيق + المصادقة (JWT) + التوجيه للمسار الصحيح
      ▼
[4] Business Logic Layer
      │  تطبيق قواعد العمل + التحقق من الصلاحيات (RBAC)
      ▼
[5] Integration Layer
      │  تنسيق الاتصال بين الوحدات + كتابة سجل التدقيق (متى لزم)
      ▼
[6] Database Layer (PostgreSQL)
      │  تنفيذ الاستعلام / المعاملة (Transaction)
      ▼
   الاستجابة تعود بنفس المسار صعودًا بتنسيق JSON موحّد:
   { "status": "success|fail", "data": {...}, "error": null|"رسالة الخطأ" }
```

---

## 2. تدفق إجراء: تسجيل فرد جديد (FR-01)

1. **Client** → المستخدم يملأ نموذج فرد جديد ويضغط "حفظ".
2. **API** → `POST /api/v1/personnel` مع Bearer Token.
3. **Business Logic**:
   - التحقق من JWT وصلاحية "إدارة الأفراد".
   - التحقق من الحقول الإلزامية (`full_name` غير فارغ).
   - التحقق من وجود `rank_id` و`unit_id` في قاعدة البيانات (سلامة مرجعية).
4. **Database** → إدراج سجل في `Personnel`.
5. **Integration Layer** → إدراج سجل موازٍ في `AuditLogs` (نفس المعاملة أو معاملة تالية فورية).
6. **الاستجابة** → 201 مع بيانات السجل الجديد، أو 400 مع تفاصيل الخطأ.

---

## 3. تدفق إجراء: طلب انتقال فرد بين معسكرين (FR-09) — الأكثر حساسية

هذا الإجراء يتطلب **معاملة قاعدية موحّدة (Atomic Transaction)** لأنه يمس أكثر من جدول:

1. **Client** → تقديم طلب نقل (`personnel_id`, `camp_from`, `camp_to`).
2. **API** → `POST /api/v1/transfers`.
3. **Business Logic**:
   - التحقق من صلاحية "إدارة الانتقالات".
   - التحقق من سعة المعسكر الهدف (`Camps.capacity` مقابل عدد الأفراد الحاليين).
4. **بدء Transaction**:
   - أ. تحديث `Personnel.unit_id` إلى الوحدة الجديدة.
   - ب. إدراج سجل جديد في `Transfers` (`camp_from`, `camp_to`, `transfer_id`).
   - ج. إدراج سجل في `PersonnelStatus` إن استلزم الانتقال تغيير الحالة.
5. **Commit** — إذا نجحت كل الخطوات الثلاث، وإلا **Rollback** كاملًا.
6. **Integration Layer** → تسجيل تدقيقي فوري في `AuditLogs`.
7. **الإشعارات (Should-Have)** → إشعار لمدير المعسكر المستقبِل.
8. **الاستجابة** → 201 عند التفعيل الناجح لمعاملة موحّدة.

## 4. تدفق إجراء: توليد تقرير إحصائي (FR-13)

1. **Client** → طلب تقرير مع فلاتر (تاريخ/معسكر/حالة).
2. **API** → `GET /api/v1/reports/summary?filters...`.
3. **Business Logic** → التحقق من صلاحية "عرض التقارير".
4. **Database** → استعلامات تجميعية (`GROUP BY`, `COUNT`, `JOIN`) عبر جداول `Personnel`, `Camps`, `Assignments`.
5. **Business Logic** → تحويل النتائج إلى تنسيق PDF/Excel عند الطلب.
6. **الاستجابة** → ملف جاهز للتنزيل أو JSON منسّق لعرضه في لوحة التحكم.

---

## 5. تدفق إجراء: تسجيل الدخول والمصادقة

1. **Client** → إرسال `username` / `password`.
2. **API** → `POST /api/v1/auth/login`.
3. **Business Logic**:
   - جلب `password_hash` من جدول `Users`.
   - مقارنة عبر `bcrypt.compare()`.
   - عند النجاح: توليد JWT موقّع يحمل `user_id`, `role_id`, صلاحية زمنية محدودة.
4. **الاستجابة** → 200 مع الرمز، أو 401 عند الفشل (رسالة عامة لا تكشف أي الحقلين خاطئ).
5. **Rate Limiting** → بعد عدد محاولات فاشلة محدد، يُحظر الحساب مؤقتًا لمنع هجمات التخمين.

---

## 6. مبدأ عام يحكم كل التدفقات

- **حدود الوحدات (Module Boundaries):** كل تدفق يمر حصريًا عبر واجهات API موثّقة داخليًا — لا وحدة تصل مباشرة لقاعدة بيانات وحدة أخرى.
- **الاستجابة الموحّدة دائمًا:** `status` / `data` / `error` بغض النظر عن نوع العملية.
- **كل عملية حساسة تُسجَّل** في `AuditLogs` بشكل غير قابل للتعديل، مع الطابع الزمني وهوية المستخدم.
