# Memory — ملف الذاكرة المرجعية للمشروع

> هذا الملف يُقرأ أولًا في بداية أي جلسة عمل (بشرية أو مع نموذج ذكاء اصطناعي) لاستعادة كامل سياق المشروع بسرعة دون الحاجة لإعادة شرح كل شيء من الصفر. يجب تحديثه كلما تغيّر قرار مهم أو اكتملت مرحلة.

---

## 1. هوية المشروع

- **الاسم:** نظام إدارة شؤون الأفراد والمعسكرات
- **بالإنجليزية:** Integrated Personnel and Camps Management System
- **الجهة:** جامعة تعز — كلية الحاسوب وتقنية المعلومات — قسم تقنية المعلومات
- **النوع:** مشروع تخرج رقم 21 — دراسة جدوى شاملة (المستوى الرابع)
- **طبيعة البيانات:** بيانات افتراضية بالكامل لأغراض أكاديمية — **لا** تتضمن أي معلومات عسكرية أو حساسة حقيقية

## 2. القرارات المعمارية الثابتة (لا تُغيَّر دون مراجعة صريحة)

| القرار | القيمة | السبب |
|---|---|---|
| نمط المعمارية | Modular Monolith (Layered) | يناسب فريقًا طلابيًا وجدولًا زمنيًا 16 أسبوعًا |
| الواجهة الأمامية | React.js SPA | — |
| بروتوكول API | REST / JSON، بادئة `/api/v1/...` | ثبات النسخة والتوافق المستقبلي |
| قاعدة البيانات | PostgreSQL | 13 جدولًا، صيغة طبيعية 3NF |
| المصادقة | JWT + bcrypt | صلاحية زمنية محدودة، لا يُخزَّن الرمز في localStorage |
| التفويض | RBAC على مستوى كل نقطة API | مبدأ أقل الصلاحيات |
| شكل الاستجابة | `{status, data, error}` موحّد لكل نقاط النهاية | — |
| لغة الكود | TypeScript في الخادم والواجهة معًا | ضمان تكامل عقود الـAPI وشكل الاستجابة الموحّد |
| خلفية الخادم | Node.js + Express | بيئة MERN التقليدية وتوثيق واسع يناسب الفريق الطلابي |
| ORM / قاعدة البيانات | Prisma مع PostgreSQL محلي مثبّت على الجهاز | توليد المخطط + الترحيلات (Migrations) + استعلامات آمنة مكتوبة بنوع |

| مكتبة الواجهة | Tailwind CSS + shadcn/ui مع تفعيل RTL (اقتران `dir="rtl"`) | دعم مباشر لخاصية `rtl:true` في Tailwind + مكوّنات نسخة (Copy-paste) بلا قيود ترخيص |
| أدوات التطوير | Vite (واجهة)، Vitest + Supertest (اختبارات)، لا Docker — Postgres مثبّت يدويًا | اختيارات الفريق الموثّقة في AGENTS.md |

## 3. نطاق المشروع (لا يتم تجاوزه)

**Must-Have (MVP):** إدارة الأفراد، إدارة المعسكرات، إدارة المستخدمين، المصادقة والصلاحيات الأساسية، التعيينات، واجهات API الأساسية، قاعدة البيانات، لوحة تحكم رئيسية، تقارير أساسية.

**Should-Have:** إدارة الانتقالات الكاملة، سجلات التدقيق الكاملة، البحث المتقدم، التقارير القابلة للتصدير.

**Could-Have (لاحقًا، خارج الـ16 أسبوعًا):** تحليلات متقدمة، تكاملات مع أنظمة خارجية، إشعارات فورية.

**Won't-Have (خارج النطاق نهائيًا):** أي وظائف تشغيلية أو عسكرية حقيقية، أو تعامل مع بيانات سرّية أو حساسة فعلية.

> ⚠️ أي طلب مستقبلي يقع ضمن "Won't-Have" يجب رفضه أو تحويله لملاحظة في "التطويرات المستقبلية" فقط، وليس تنفيذه.

## 7. قواعد ثابتة يجب تذكّرها دائمًا

1. لا حذف فعلي لأي سجل فرد — التعطيل منطقي (Soft Delete) فقط.
2. حالة الفرد (`PersonnelStatus`) تُحفظ تاريخيًا تراكميًا، لا تُكتب فوق السجل القديم.
3. عملية النقل بين المعسكرات **يجب** أن تكون معاملة قاعدية موحّدة (Transaction) — لا حالات نصف منفّذة.
4. كل عملية حسّاسة تُسجَّل تلقائيًا في `AuditLogs` من طبقة التكامل، وليس من الواجهة.
5. لا نقطة API تُستثنى من التحقق من الصلاحية (RBAC) — حتى لو بدت "غير حساسة".
6. أي تعديل معماري جوهري يجب أن يُسجَّل أولًا هنا (القسم 2) قبل التنفيذ.

## 9. حالة الاستئناف — أين توقفنا (يُحدَّث بعد كل جلسة)

### ما تم تنفيذه والتحقق منه (2026-09-26)
- تثبيت الاعتمادات وإنشاء `package-lock.json`.
- إصلاح العلاقات الناقصة في مخطط Prisma وإضافة الـ migration الأولية `server/prisma/migrations/20260926161305_init/`.
- إصلاح التحقق من JWT، وإضافة RBAC لقوائم المعسكرات والوحدات والرتب والمناصب والتعيينات، وحماية نقطة الصحة، وإضافة Zod لتحديث المستخدم.
- نجح `npm run typecheck -w server` و`npm run build -w server`.
- نجحت `npm run db:migrate -w server -- --name init` و`npm run db:seed -w server` على قاعدة PostgreSQL محلية معزولة.
- نجحت اختبارات الخادم: **14 اختبارًا** في `server/tests/api.test.ts` على قاعدة الاختبار المنفصلة `personnel_camps_test`.
- بيانات قاعدة البيانات محلية واصطناعية فقط. ملف `server/.env` مستثنى في `.gitignore` ولا يُرفع.

### ما لم يُنفَّذ بعد (الخطوات التالية بالترتيب)
1. بناء `client/` باستخدام Vite + React + TypeScript + Tailwind، مع RTL عربي كامل وفق `UI-UX-Specification.md`.
2. تنفيذ شاشات Phase 1 الأساسية وربطها بـAPI الفعلي دون بيانات Mock: تسجيل الدخول، لوحة التحكم، الأفراد وسجل الحالة، المعسكرات، الوحدات، الرتب/المناصب، التعيينات، وإدارة المستخدمين والتقارير الأساسية.
3. بعد إضافة مساحة عمل `client`، تحديث `package-lock.json` والتحقق من `npm run dev` و`npm run build` و`npm run typecheck` من الجذر.
4. استكمال تغطية الاختبارات لبقية عمليات CRUD والـRBAC قبل إعلان اكتمال Phase 1.
5. تحديث قوائم Phase 1 فقط بعد تحقق معايير القبول، ثم تسجيل اكتمال المرحلة في هذا الملف.

### قيود ونقاط متابعة
- لا تُضف أي وظائف تشغيلية أو عسكرية حقيقية أو بيانات حساسة فعلية؛ بيانات المشروع افتراضية/أكاديمية فقط.
- يجب أن تبقى قاعدة الاختبار منفصلة وقابلة لإعادة الضبط فقط ضمن بيئة اختبار معزولة.
- بيانات الدخول الافتراضية `admin / Admin@1234` للتطوير المحلي فقط، ويجب تغييرها قبل أي نشر.
- لا تنشأ ميزات الانتقالات الكاملة أو الإشعارات أو التحليلات المتقدمة مبكرًا؛ اتبع MoSCoW والمرحلة الحالية في `Todo-Phase-1.md`.
