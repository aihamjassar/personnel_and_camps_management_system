# Memory — ملف الذاكرة المرجعية للمشروع

> هذا الملف يُقرأ أولًا في بداية أي جلسة عمل (بشرية أو مع نموذج ذكاء اصطناعي) لاستعادة كامل سياق المشروع بسرعة دون الحاجة لإعادة شرح كل شيء من الصفر. يجب تحديثه كلما تغيّر قرار مهم أو اكتملت مرحلة.

---

## 1. هوية المشروع

- **الاسم:** نظام إدارة شؤون الأفراد والمعسكرات
- **بالإنجليزية:** Integrated Personnel and Camps Management System
- **الجهة:** جامعة تعز — كلية الحاسوب وتقنية المعلومات — قسم تقنية المعلومات
- **النوع:** مشروع تخرج رقم 21 — دراسة جدوى شاملة (المستوى الرابع)
- **طبيعة البيانات:** بيانات افتراضية بالكامل لأغراض أكاديمية — **لا** تتضمن أي معلومات عسكرية أو حساسة حقيقية

## 3. نطاق المشروع (لا يتم تجاوزه)

**Must-Have (MVP):** إدارة الأفراد، إدارة المعسكرات، إدارة المستخدمين، المصادقة والصلاحيات الأساسية، التعيينات، واجهات API الأساسية، قاعدة البيانات، لوحة تحكم رئيسية، تقارير أساسية.

**Should-Have:** إدارة الانتقالات الكاملة، سجلات التدقيق الكاملة، البحث المتقدم، التقارير القابلة للتصدير.

**Could-Have (لاحقًا، خارج الـ16 أسبوعًا):** تحليلات متقدمة، تكاملات مع أنظمة خارجية، إشعارات فورية.

**Won't-Have (خارج النطاق نهائيًا):** أي وظائف تشغيلية أو عسكرية حقيقية، أو تعامل مع بيانات سرّية أو حساسة فعلية.

> ⚠️ أي طلب مستقبلي يقع ضمن "Won't-Have" يجب رفضه أو تحويله لملاحظة في "التطويرات المستقبلية" فقط، وليس تنفيذه.

## 7. قواعد ثابتة يجب تذكّرها دائمًا

1. لا حذف فعلي لأي سجل فرد — التعطيل منطقي (Soft Delete) فقط.
2. حالة الفرد (`PersonnelStatus`) تُحفظ تاريخيًا تراكميًا، لا تُكتب فوق السجل القديم.
3. عملية النقل بين المعسكرات **يجب** أن تكون معاملة قاعدية موحّدة (Transaction) — لا حالات نصف منفّذة.
4. كل عملية حسّاسة تُسجَّل تلقائيًا في `AuditLogs` من طبقة التكامل، وليس من الواجهة.
5. لا نقطة API تُستثنى من التحقق من الصلاحية (RBAC) — حتى لو بدت "غير حساسة".
6. أي تعديل معماري جوهري يجب أن يُسجَّل أولًا هنا (القسم 2) قبل التنفيذ.

## 9. حالة الاستئناف — أين توقفنا (يُحدَّث بعد كل جلسة)

### ما تم تنفيذه والتحقق منه (2026-09-26)

- ثُبّتت الاعتمادات في workspaces الخادم والواجهة، وأُنشئ `package-lock.json`.
- أُصلحت العلاقات الناقصة في Prisma وأُضيفت migration أولية `server/prisma/migrations/20260926161305_init/`، مع إعداد قاعدة تطوير محلية منفصلة وseed أكاديمي.
- حُسّن التحقق من JWT وRBAC والتحقق من مدخلات تحديث المستخدم. نقاط قراءة المراجع تُتاح فقط للأدوار التي تحتاجها نماذج Phase 1، مع بقاء الكتابة مقيدة بصلاحيات الإدارة المناسبة.
- أُنشئت مساحة `client/` باستخدام React + TypeScript + Vite + Tailwind. الواجهة عربية RTL ومتّصلة بالـAPI الحقيقي، وتشمل الدخول والملخص والأفراد والحالات والسجل التاريخي والمعسكرات والوحدات والرتب والمناصب والتعيينات وإدارة المستخدمين.
- تُخزَّن الجلسة في `sessionStorage`، وتُفرض صلاحيات المسارات في الواجهة إلى جانب RBAC على الخادم. أضيفت حالات التحميل/الخطأ/الفراغ، ومكونات جدول وواجهة مشتركة، ونوافذ قابلة للوصول للتأكيد والتعديل.
- توسعت اختبارات `server/tests/api.test.ts` لتغطي CRUD للمراجع، تعاقب التعيينات ضمن المعاملة، إنشاء/تحديث المستخدم، سجل التدقيق، والتحكم بالصلاحيات. اجتازت مجموعة الاختبارات **16/16** على قاعدة الاختبار المنفصلة `personnel_camps_test`.
- نجحت أوامر الجذر `npm run typecheck` و`npm run build` و`npm test`. إنشاء البناء الأمامي أنتج حزمة Vite قابلة للنشر.
- أُجريت اختبارات متصفح يدوية ببيانات اصطناعية: تسجيل الدخول، الملخص، إنشاء معسكر ووحدة وفرد وتعيين وحساب Viewer، تحديث الحالة والتحقق من عدم استبدال سجلها، وحجب المسار المباشر لمستخدم التقرير. التفاصيل في `docs/browser-verification.md`.
- أُضيف `README.md` لإعداد البيئة وتشغيلها، وحُدّث `docs/Todo-Phase-1.md` لتعكس التسليم الحالي.
- ملف `server/.env` محلي ومتجاهل بواسطة Git؛ لا تُضمّن أسرار البيئة في أي commit أو مشاركة.

### الخطوات التالية

Phase 1 مكتملة محليًا. قبل النشر الفعلي يلزم تغيير بيانات الدخول الافتراضية، وتوفير PostgreSQL وسر JWT آمنين، وإعداد HTTPS، وبيئة نشر مستقلة. المرحلة التالية حسب MoSCoW هي Phase 2؛ لا تبدأ تنفيذ نقل شامل بين المعسكرات أو إشعارات أو تحليلات متقدمة ضمن هذا التسليم.

### قيود ونقاط متابعة

- جميع بيانات التطوير والاختبار والعرض اصطناعية لأغراض أكاديمية فقط؛ لا تُدخل بيانات حقيقية أو حساسة ولا تضف ميزات تشغيلية.
- قاعدة `personnel_camps_test` مخصصة للاختبارات وتُعاد تهيئتها عند كل تشغيل للاختبارات؛ يجب أن تظل منفصلة عن التطوير والإنتاج.
- بيانات الدخول `admin / Admin@1234` للتطوير المحلي فقط ويجب تغييرها قبل أي نشر.
- لا تُنفّذ الميزات المؤجلة (الانتقالات الكاملة، الإشعارات، التحليلات المتقدمة أو التصدير المتقدم) قبل المرحلة المقررة لها.
