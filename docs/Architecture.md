# معمارية النظام (Architecture)

---

## 1. نمط المعمارية المعتمد

**Modular Monolith بتصميم طبقي (Layered Architecture)**

| البديل | الملاءمة لنطاق المشروع | السبب |
|---|---|---|
| ✅ **Modular Monolith (طبقي)** | **موصى به** | يوفّر فصلًا واضحًا للوحدات مع تعقيد تشغيلي منخفض يناسب فريقًا طلابيًا وجدولًا محدودًا (16 أسبوعًا) |
| ❌ Service-Oriented Architecture | متوسطة | تتطلب بنية اتصال أكثر تعقيدًا (Message Broker) لا تبررها حجم البيانات الافتراضية |
| ❌ Microservices | غير مناسبة حاليًا | تتطلب بنية تحتية للنشر والمراقبة والتنسيق تفوق موارد فريق طلابي وخبرة 16 أسبوعًا |

## 2. الطبقات المعمارية الست

```
┌─────────────────────────────────────────────┐
│ 1. طبقة العميل (Client) — React.js SPA       │
├─────────────────────────────────────────────┤
│ 2. طبقة الواجهة الأمامية / العرض             │
│    (لوحات التحكم، النماذج، التقارير المرئية) │
├─────────────────────────────────────────────┤
│ 3. طبقة API (REST / JSON)                    │
│    (المصادقة، الموجّه، معالجة الطلبات)        │
├─────────────────────────────────────────────┤
│ 4. طبقة منطق الأعمال (Business Logic)        │
│    (قواعد الأفراد، المعسكرات، الانتقالات،     │
│     الصلاحيات)                                │
├─────────────────────────────────────────────┤
│ 5. طبقة التكامل (Integration Layer)          │
│    (تنسيق الاتصال بين الوحدات + سجل التدقيق) │
├─────────────────────────────────────────────┤
│ 6. طبقة البيانات (Database Layer)            │
│    (PostgreSQL — جداول الأفراد، المعسكرات،   │
│     المستخدمين...)                           │
└─────────────────────────────────────────────┘
```

**مبدأ حدود الوحدات (Module Boundaries):** يُصمَّم النظام بحيث تبقى حدود كل وحدة (أفراد، معسكرات، مستخدمين...) واضحة عبر واجهات API داخلية موثّقة، بما يسمح بالتطور المستقبلي نحو خدمات مصغّرة دون إعادة كتابة جوهرية.

## 4. تصميم واجهات برمجة التطبيقات (API Design)

### 4.1 قاعدة التسمية
جميع واجهات النظام تتبع نمط تسمية موحّد يبدأ بالإصدار (`/api/v1/...`) لضمان قابلية التطور دون كسر التوافق.

### 4.2 أهم نقاط النهاية (من جدول 13-1 في دراسة الجدوى)

| الطريقة | المسار | الغرض | المصادقة | ملاحظات |
|---|---|---|---|---|
| POST | `/api/v1/auth/login` | تسجيل الدخول وإصدار رمز JWT | لا يتطلب | 200 عند النجاح، 401 عند الفشل |
| GET | `/api/v1/personnel` | استعراض قائمة الأفراد مع دعم الترشيح والصفحات | Bearer Token | 200 مع قائمة مرقّمة الصفحات |
| POST | `/api/v1/personnel` | إضافة سجل فرد جديد | صلاحية "إدارة الأفراد" | 201 عند النجاح، 400 عند بيانات غير صالحة |
| PUT | `/api/v1/personnel/{id}` | تحديث بيانات فرد | صلاحية "إدارة الأفراد" | 200 عند النجاح، 404 إذا لم يوجد السجل |
| POST | `/api/v1/transfers` | تقديم طلب انتقال فرد بين معسكرين | صلاحية "إدارة الانتقالات" | 201 مع تفعيل معاملة قاعدية موحّدة وتسجيل تدقيقي تلقائي |
| GET | `/api/v1/reports/summary` | تقرير إحصائي شامل عن الأفراد والمعسكرات | صلاحية "عرض التقارير" | 200 مع بيانات مجمّعة قابلة للتصدير JSON |
| GET | `/api/v1/audit` | استعراض سجل التدقيق مع الترشيح بالتاريخ والمستخدم | صلاحية "مدير النظام" | 200 مع قائمة مرتبة زمنيًا |

### 4.3 نموذج الاستجابة الموحّد

```json
{
  "status": "success | fail",
  "data": { },
  "error": null
}
```

جميع نقاط النهاية تعتمد هذا الشكل الموحّد لتسهيل تكامل الواجهة الأمامية مع الخلفية دون معالجة استثنائية لكل نقطة نهاية.

## 5. تصميم قاعدة البيانات

### 5.1 الجداول الرئيسية (13 جدولًا)

| الجدول | المفتاح الأساسي | الوصف |
|---|---|---|
| Users | user_id | حسابات مستخدمي النظام |
| Roles | role_id | الأدوار الوظيفية (مدير نظام، ضابط أفراد...) |
| Permissions | permission_id | الصلاحيات الدقيقة الفابلة للربط بالأدوار |
| Personnel | personnel_id | سجلات الأفراد الأساسية والوظيفية |
| Camps | camp_id | بيانات المعسكرات (الاسم، السعة، الموقع الافتراضي) |
| OrganizationalUnits | unit_id | الوحدات التنظيمية وربطها بالمعسكرات |
| Ranks | rank_id | الرتب الوظيفية وتسلسلها |
| Positions | position_id | المناصب الإدارية المرتبطة بالوحدات |
| Assignments | assignment_id | تعيين فرد في منصب/وحدة لفترة محددة |
| Transfers | transfer_id | طلبات وسجلات انتقال الأفراد بين المعسكرات |
| PersonnelStatus | status_id | سجل تاريخي لحالات الفرد المختلفة |
| AuditLogs | log_id | سجل تفصيلي لجميع العمليات الحسّاسة |
| Notifications | notification_id | إشعارات المستخدمين |

### 5.2 العلاقات الأساسية (ER)

- `Users` — `Roles`: علاقة متعدد لمتعدد (Many-to-Many) عبر جدول ربط `UserRoles`.
- `Roles` — `Permissions`: علاقة متعدد لمتعدد عبر جدول ربط `RolePermissions`.
- `Camps` — `OrganizationalUnits`: علاقة واحد لمتعدد (One-to-Many).
- `OrganizationalUnits` — `Personnel`: علاقة واحد لمتعدد.
- `Personnel` — `Assignments`: علاقة واحد لمتعدد (قد يملك الفرد أكثر من سجل تعيين تاريخيًا).
- `Personnel` — `Transfers`: علاقة واحد لمتعدد (لتتبّع كل عمليات انتقال الفرد عبر الزمن).
- `Personnel` — `PersonnelStatus`: علاقة واحد لمتعدد (لحفظ السجل التاريخي الكامل لحالات الفرد).
- `Users` — `AuditLogs`: علاقة واحد لمتعدد (كل مستخدم قد يُنشئ عدة سجلات تدقيق).

### 5.3 قواعد التصميم
- الجداول مصمَّمة وفق الصيغة الطبيعية الثالثة (3NF) لتقليل التكرار.
- تُفرض السلامة المرجعية (Referential Integrity) عبر قيود المفاتيح الأجنبية بحيث لا يمكن، على سبيل المثال، حذف معسكر مرتبط بوحدات تنظيمية فعّالة دون معالجة صريحة لتلك التبعية.

## 6. طبقة الأمان المطبَّقة معماريًا

| الجانب الأمني | آلية التطبيق |
|---|---|
| المصادقة (Authentication) | JWT يصدر عند تسجيل دخول موحّد، محدود الصلاحية الزمنية |
| التفويض (Authorization) | RBAC — التحكم بالوصول على أساس الأدوار على مستوى كل نقطة API |
| تجزئة كلمات المرور | bcrypt لتخزين كلمات المرور بدل النص الصريح |
| النقل الآمن | HTTPS لتشفير جميع الاتصالات بين المتصفح والخادم |
| التحقق من المدخلات | تحقق صارم من نوع وطول وصيغة كل حقل قبل معالجته |
| منع حقن SQL | استخدام الاستعلامات المُعامَلة (Parameterized Queries) أو ORM آمن |
| منع XSS | تنقية المدخلات وتشفير المخرجات المعروضة في الواجهة |
| أمان واجهات API | التحقق من الرمز في كل طلب + التحقق من نطاق الصلاحية |
| الحد من معدل الطلبات (Rate Limiting) | تقييد عدد المحاولات لتسجيل الدخول لمنع هجمات التخمين |
| سجل التدقيق | تسجيل كل عملية حسّاسة مع هوية المستخدم والطابع الزمني |
| أمان النسخ الاحتياطي | تشفير النسخ الاحتياطية وتقييد الوصول إليها |
| مبدأ أقل الصلاحيات | منح كل دور الحد الأدنى من الصلاحيات اللازمة لأداء مهامه فقط |
| أمان الجلسات | انتهاء صلاحية الجلسة تلقائيًا بعد فترة خمول محددة |

## 8. أدوار الفريق المرتبطة بالمعمارية

| الدور | الطبقة المسؤول عنها |
|---|---|
| مطوّر الخلفية (API Developer) | طبقة API + منطق الأعمال + ربط قاعدة البيانات |
| مطوّر الواجهة الأمامية | طبقة العميل والعرض |
| مهندس تكامل الأنظمة والمعمارية | طبقة التكامل + تنسيق تدفق البيانات بين الوحدات |
| مهندس قاعدة البيانات / الأمان | طبقة البيانات + الضوابط الأمنية عبر كل الطبقات |
