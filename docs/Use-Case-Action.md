# إجراءات حالات الاستخدام (Use Case Actions)
## تفصيل كل إجراء على مستوى الواجهة، الـ API، وقاعدة البيانات

> هذا الملف يوسّع كل سيناريو من `Use-Case-Scenario.md` إلى خطوات تنفيذية مباشرة (Action-Level) يمكن للمطوّر تتبعها حرفيًا.

---

## UC-01 — تسجيل الدخول

| # | الإجراء | الطبقة | التفاصيل التقنية |
|---|---|---|---|
| 1 | إدخال بيانات الاعتماد | Frontend | نموذج React يتحقق من الحقول الفارغة قبل الإرسال |
| 2 | إرسال الطلب | API | `POST /api/v1/auth/login` — Body: `{username, password}` |
| 3 | التحقق من الهوية | Business Logic | مقارنة hash كلمة المرور عبر bcrypt |
| 4 | إصدار الرمز | Business Logic | توليد JWT يحمل `sub` و`username` مع انتهاء محدد؛ تُحمّل الصلاحيات النشطة من قاعدة البيانات عند كل طلب |
| 5 | حفظ الجلسة | Frontend | تخزين الرمز في `sessionStorage` واستخدامه في ترويسة Bearer؛ لا يُستخدم `localStorage` |
| 6 | التوجيه | Frontend | التوجيه للوحة التحكم بحسب الدور |

**الاستجابة الموحّدة:** `{status, data, error}` — طبقًا لنموذج الاستجابة القياسي في القسم 13.3 من دراسة الجدوى.

## UC-02 — تسجيل فرد جديد (FR-01)

| # | الإجراء | الطبقة | التفاصيل التقنية |
|---|---|---|---|
| 1 | فتح نموذج الإضافة | Frontend | نموذج بحقل `full_name` مطلوب وحقول اختيارية مثل `rank_id`, `unit_id`, `camp_id` |
| 2 | التحقق الأولي | Frontend | الاسم الكامل فقط إلزامي؛ الحالة الابتدائية `active` يعيّنها الخادم |
| 3 | إرسال الطلب | API | `POST /api/v1/personnel` — يتطلب Bearer Token |
| 4 | التحقق من الصلاحية | Business Logic | صلاحية "إدارة الأفراد" فقط (RBAC) |
| 5 | التحقق من قواعد العمل | Business Logic | يتحقق الخادم من مخطط الطلب ومفاتيح العلاقات الاختيارية |
| 6 | الإدراج في القاعدة | Database | إدراج سجل `Personnel` بالحالة الابتدائية `active` وإضافة صف أولي في `PersonnelStatus` |
| 7 | تسجيل تدقيقي | Integration Layer | إدراج سجل في `AuditLogs` (من قام، بماذا، متى) |
| 8 | الاستجابة | API | 201 عند النجاح، 400 عند بيانات غير صالحة |

## UC-03 — تعديل/حذف بيانات فرد (FR-02)

| # | الإجراء | الطبقة | التفاصيل |
|---|---|---|---|
| 1 | البحث عن السجل | Frontend/API | العثور عليه في قائمة `GET /api/v1/personnel` (لا توجد نقطة `GET /:id` مستقلة حاليًا) |
| 2 | تعديل الحقول | Frontend | نموذج معبأ مسبقًا (Pre-filled Form) |
| 3 | إرسال التحديث | API | `PUT /api/v1/personnel/{id}` |
| 4 | التحقق من الصلاحية والوجود | Business Logic | 404 إذا لم يوجد السجل، 403 إذا لا يملك صلاحية |
| 5 | تحديث القاعدة | Database | تحديث الحقول المعدَّلة فقط |
| 6 | تسجيل تدقيقي | Integration Layer | تسجيل القيم القديمة والجديدة |
| 7 | الحذف (اختياري) | Business Logic | تعطيل منطقي بتعيين `deleted_at` و`is_active=false`؛ لا يُحذف صف قاعدة البيانات |

## UC-04 — البحث المتقدم (FR-03)

| # | الإجراء | الطبقة | التفاصيل |
|---|---|---|---|
| 1 | اختيار معايير البحث | Frontend | حقول: الاسم / الرتبة / المعسكر / الوحدة / الحالة |
| 2 | إرسال طلب مفلتر | API | `GET /api/v1/personnel?search=&rank_id=&camp_id=&unit_id=&status=&page=&page_size=`؛ يتطلب `personnel.manage` |
| 3 | بناء الاستعلام | Business Logic | استخدام Parameterized Queries لمنع SQL Injection |
| 4 | إرجاع النتائج | API | استجابة مقسّمة بالصفحات (Pagination) — 200 |

## UC-05 — تحديث حالة الفرد (FR-04)

| # | الإجراء | الطبقة | التفاصيل |
|---|---|---|---|
| 1 | اختيار الحالة الجديدة | Frontend | قائمة منسدلة: `active` / `inactive` / `on_leave` / `transferred` / `discharged` |
| 2 | إرسال الطلب | API | `POST` إلى نقطة نهاية حالة الفرد ضمن `/api/v1/personnel/{id}` |
| 3 | إنشاء سجل تاريخي | Database | إدراج سجل جديد في `PersonnelStatus` (لا تحديث فوق القديم) |
| 4 | إشعار (اختياري Should-Have) | Integration Layer | إرسال إشعار للمعنيين عند تغيير حساس |

| # | الإجراء | الطبقة | التفاصيل |
|---|---|---|---|

## UC-07 — إدارة الانتقالات (FR-09)

| # | الإجراء | الطبقة | التفاصيل |
|---|---|---|---|
| 1 | تأكيد نقل فوري | API | `POST /api/v1/transfers` — `{personnel_id, camp_from_id, camp_to_id, unit_to_id, reason?}` |
| 2 | بدء معاملة موحّدة | Business Logic / Integration Layer | تتحقق العملية من المعسكر الحالي والوحدة والسعة، ثم تحدّث الفرد وتدرج `Transfer` والتدقيق ذريًا |
| 3 | التحقق من السعة | Business Logic | مقارنة عدد الأفراد الحاليين بـ `capacity` في `Camps` |
| 4 | تسجيل تدقيقي تلقائي | Integration Layer | إدراج في `AuditLogs` فور تفعيل المعاملة |
| 5 | الاستجابة | API | 201 عند التنفيذ؛ يسجل النقل `completed` مباشرة ولا توجد موافقة لاحقة في النسخة الحالية |

## UC-13 — إعدادات النظام (FR-16)

| # | الإجراء | الطبقة | التفاصيل |
|---|---|---|---|
| 1 | فتح شاشة الإعدادات | Frontend | متاحة فقط لدور "مدير النظام" |
| 2 | قراءة الإعدادات | API | `GET /api/v1/settings` — صلاحية `system.admin` فقط |
| 3 | تعديل سياسة كلمة المرور ومدة الجلسة | API | `PUT /api/v1/settings` — تحقق من حد الطول (8–64)، مدة الجلسة (1–24 ساعة)، وقيم القواعد المنطقية |
| 4 | إرشاد مدير المستخدمين | API | `GET /api/v1/settings/password-policy` — `users.manage` أو `system.admin`، يعيد قواعد كلمة المرور فقط |
| 5 | الحفظ والتدقيق | Database / Integration | تحديث جدول `system_settings` وتسجيل `SystemSettingChanged` في نفس المعاملة؛ لا تُسجّل أي أسرار |
| 6 | تطبيق السياسة | Business Logic | التحقق من سياسة كلمة المرور عند إنشاء حساب أو إعادة تعيينها؛ تطبيق مدة الجلسة على رموز الدخول الجديدة فقط |
